# 02: Architecture

## Rust or not?

**Rust isn't silly. It's the right call for the engine, as long as Swift owns the UI.**

### What goes where

| Layer | Language | Why |
|---|---|---|
| Every pixel: windows, notch, menu bar, Liquid Glass, animations | **Swift / SwiftUI + AppKit** | Only Apple's frameworks give real Liquid Glass, native text, accessibility, notch windows, and the feel people pay for |
| Everything Apple-only: EventKit, Contacts, Vision OCR, ScreenCaptureKit, AVFoundation, Foundation Models, App Intents, CloudKit, WidgetKit, Keychain | **Swift** | First-class Swift APIs. Wrapping them in Rust adds pain for no gain |
| The engine: storage, search, indexing, sync change-sets, agent runtime, tools/MCP, connectors (IMAP, Gmail, Graph, Xero), parsing (mail, docs, sheets), scheduling, budgets, audit log | **Rust** | Fast, memory-safe, fearless concurrency for background work. **Portable to iPhone (same core), and to Windows/Linux later.** Large crate ecosystem (tantivy, sqlite, IronCalc, Typst, Harper, mail-parser) |
| Model inference | **Swift for MLX + Apple FM** (in an XPC helper), **Rust for HTTP providers** | MLX is fastest on Apple Silicon and its best binding is `mlx-swift-lm`. Cloud and OpenAI-compatible calls are plain HTTP in Rust |
| User-made mini-apps (from Johnny) | **HTML/JS** in a sandboxed `WKWebView` | Safe, flexible, generated by AI easily, styled from the same design tokens |
| User scripts | **JavaScript (JavaScriptCore)** or **WASM (wasmtime)** | Built into macOS (JSC), sandboxable, no Python install |

### The bridge
- **UniFFI** (Mozilla, MPL-2.0) generates Swift bindings from Rust. Expose a **coarse, async API**: `bolton.search(query) async -> SearchResults`, not hundreds of tiny calls.
- Swift supplies capabilities *into* Rust through UniFFI **callback interfaces**: `CalendarProvider`, `ContactsProvider`, `OCRProvider`, `ModelProvider (Apple FM / MLX)`, `KeychainProvider`, `NotificationSink`. The Rust core never imports Apple frameworks directly. That keeps it portable and testable.
- Package the core as an **XCFramework** (`cargo-swift` or a small script around `cargo build --target aarch64-apple-darwin / aarch64-apple-ios / aarch64-apple-ios-sim` + `xcodebuild -create-xcframework`).

### Honest costs of Rust, and how to manage them
| Cost | Mitigation |
|---|---|
| Two languages to learn and debug | Keep the boundary small and typed. AI coding tools are strong at Rust. The compiler catches most mistakes |
| Build complexity (XCFramework, bindings regeneration) | One `make core` script. CI checks bindings are fresh. Commit generated Swift |
| Async across FFI | UniFFI supports async functions mapped to Swift `async`. Run a single Tokio runtime inside the core |
| Slower UI iteration if logic sits behind FFI | Put view models in Swift. Rust returns plain data records |

### Alternatives considered (and why not)
| Option | Verdict |
|---|---|
| **Pure Swift** | Viable and simplest for Apple-only. But you'd hand-build search, sync and mail engines in Swift, with no Windows path and a smaller library ecosystem. Use it as the fallback if Rust slows you down badly in month one |
| **Tauri (Rust + web UI)** | Reuses your React/Next.js skills, but can't do real Liquid Glass or a native feel. The notch needs native plugins anyway, and it'll feel like a web app |
| **Electron** | No: heavy, battery-hungry, and against the "runs on an 8 GB Air" goal |
| **Keep Next.js + Postgres (current repo)** | Fine for a web product, wrong for a local-first Mac suite. Docker Postgres on a user's laptop is a non-starter. Salvage the logic, prompts and schemas (see [roadmap: salvage](./07-roadmap.md#salvage-from-the-current-repo)) |

### Why one always-running process
- The notch, menu bar, schedules, mail sync and the 11am check-in need something running all the time. A single process owns them.
- **Dock icon toggling:** use `NSApp.setActivationPolicy(.accessory)` when no agent windows are open (lives only in the notch and menu bar) and `.regular` when a window opens, so it gets a Dock icon and Cmd-Tab.
- **ModelHost as a separate XPC service:** models use gigabytes. Isolating them means a model crash doesn't take down the suite, and the core can kill the host to release memory instantly under pressure.

### "Each agent has an app": two stages
| Stage | How it looks | When |
|---|---|---|
| **Stage 1: Agent windows** | One `11am.app`. Each agent opens as its own window with its own toolbar identity and monogram, through `WindowGroup(id: "marc")` and friends. Window menu and ⌘1…⌘9 switch agents. | v1. Fastest to build. One binary, one update |
| **Stage 2: Suite of app bundles** | `/Applications/11am/Marc.app`, `William.app`… Each is a thin SwiftUI client (a few MB) sharing `ElevenAmKit.framework` and talking to the always-running 11am core over a **Mach XPC service** published by the login item. Each gets its own Dock icon, Cmd-Tab entry, default-app registration (Marc as default mail app, James as default browser) and Spotlight presence. **Purchasing an agent installs its bundle.** | After v1. This is the "Microsoft 365 suite" feel |

Design for Stage 2 from day one: every agent UI is its own Swift package (`AgentMarcUI`), with no cross-imports between agent packages. They talk only through the core.

## The core: modules and data

### Storage
- **One SQLite database per user profile** (WAL mode) at `~/Library/Application Support/11am/<profile>/11am.db`, plus domain DBs where size warrants it (`mail.db`, `index.db`). Use `rusqlite` (sync, simple) behind a Tokio blocking pool, or `sqlx`.
- **Full-text:** SQLite **FTS5** first. Move to **tantivy** only if mail or file corpora outgrow it (millions of documents).
- **Vectors:** **sqlite-vec** inside the same DB (single file, easy backup). **LanceDB** only if vectors exceed a few million.
- **Blobs:** content-addressed store (`blobs/ab/cdef…`) for attachments, thumbnails, transcripts and extracted text. **User files stay where they are.** Bolton indexes them, it doesn't copy them.
- **User-owned files:** notes as `.md`, William docs as `.md` + sidecar, Robert designs as `.11design` packages (JSON + assets), George sheets as `.xlsx`-compatible. All live in a visible `~/11am/` folder (configurable) so the user owns them and iCloud Drive or Time Machine back them up.
- **Secrets:** Keychain only (OAuth tokens, API keys).
- **Optional:** encryption at rest with SQLCipher for users without FileVault (FileVault is on by default on modern Macs, so make this a setting).

### Core tables (shared)
```
profiles(id, name, created_at)
agents(id, enabled, entitlement, autonomy_json, model_policy_json)
events(id, ts, agent, kind, subject_ref, payload_json, model, cost, undo_ref, parent_event, job_id)   -- append-only

         text, entity_ids, source_ref, confidence, valid_from, valid_to, supersedes, created_by)
```

These map directly onto the current Bolton schema (`memory_entries`, `entities`, `entity_relationships`, `decisions`, `conflicts`, `*_voice_profiles`, `*_sender_profiles`, `action_log`, `handoffs`). The concepts carry over, ported from Postgres to SQLite.

### The event log is the spine
Every agent action, tool call, model call, approval and user edit is an `events` row. This one table gives you:
- **The activity feed** ("what my team did today").
- **Leo's briefs** (summaries over events since the last check-in).
- **Undo** (`undo_ref` points to an inverse operation or a snapshot).
- **Audit and trust** (users can see exactly what happened and why).
- **Evals and learning** (approved vs edited vs rejected drafts become training signal).

## Agent runtime: how the team works

### Agent manifest (one per agent, in `registry/agents/<id>.toml`)
```toml
id = "marc"
name = "Marc"
monogram = "mc"
role = "Communication"
entitlement = "addon.marc"
default_autonomy = { draft = "auto", label = "auto", archive = "approve", send = "approve", delete = "approve" }
data_classes = ["private_messages", "contacts"]           # governs cloud eligibility
model_policy = { triage = "small.local", summarise = "medium.local", draft = "medium.prefer_local", reason = "large.ask" }
tools = ["mail.search", "mail.read", "mail.draft", "mail.send", "messages.read", "messages.send",
         "people.lookup", "bolton.context", "bolton.remember", "agent.ask"]
schedules = [{ id = "sync", every = "2m" }, { id = "triage", on = "mail.new" }, { id = "digest", cron = "0 7 * * *" }]
surfaces = ["window", "notch.approvals", "ios.triage", "intent.compose"]
```

### Tools (MCP-native)
- Every capability is a **tool** with a JSON Schema input and output, a **risk level** (`read`, `write_internal`, `write_external`, `irreversible`) and an **owner agent**.
- Tools are exposed internally *and* as an **MCP server** (`rmcp`), so Claude Desktop, Cursor and others can optionally use 11am as a tool. 11am is also an **MCP client**, so users can plug in any MCP server (Notion, Linear, GitHub…) and Johnny can generate new ones.
- The **policy engine** sits between the agent loop and every tool call: it checks entitlements, permissions, data-class rules, autonomy level and budget, and either executes, queues for approval, or refuses.

### The agent loop
```
trigger (user ask | schedule | event) → job created (budget attached)
 → load context: manifest instructions + spec rules + Bolton context pack + recent events
 → plan (model, structured JSON) → for each step:
      tool call → policy check → [execute | approval queue | refuse] → observe → (re-plan if needed)
 → result → write memories (via Bolton's curator) → event(s) → notify per notification policy
```
Port the existing `packages/jobs` ideas (queue, `budget.ts`, events, steps, sandbox) straight into `core/agents` + `core/scheduler`.

### Inter-agent protocol (keep the existing contract)
The current `AgentInvokeRequest/Response` in `apps/leo/src/lib/types.ts` is good. Keep it as Rust types on an in-process bus:
```rust
struct AgentRequest { from: AgentId, to: AgentId, task: String, context_ref: Option<Ref>,
                      priority: Priority, response_mode: ResponseMode, budget: Budget, depth: u8 }
struct AgentResponse { from: AgentId, to: AgentId, summary: String, structured: serde_json::Value,
                       memory_ids_written: Vec<MemoryId>, follow_up_needed: bool, sources: Vec<Ref> }
```
- `agent.ask` is a tool any agent can call. **Depth is capped at 3**, the child inherits a budget slice, and cycles are rejected.
- **Leo is the router for user asks, not a bottleneck.** Agents can call each other directly ("Marc asks William for voice"). Leo sees everything via the event log.
- Results land in Bolton when they're worth remembering (the curator decides). This is the existing `save-heuristic` idea from James, generalised.

### Scheduling and background work
- Tokio-based scheduler inside the core. Persisted `schedules`. Triggers: **time** (cron), **events** (`mail.new`, `file.added(folder)`, `calendar.starting(15m)`, `job.done`), **state** (on AC power, idle more than 5 min, connected to Wi-Fi).
- **Power-aware:** heavy jobs (embeddings, OCR, research synthesis, model downloads) run on AC power or when idle, via `NSBackgroundActivityScheduler` on the Swift side signalling into the queue. They respect `ProcessInfo.isLowPowerModeEnabled` and `thermalState`.
- **"Night shift":** when the Mac is charging overnight (and awake: honour the user's Energy settings; optionally schedule wake with `pmset`-style power events), run deep jobs and precompute the morning brief.

## Malleable apps: how Johnny edits apps

Users can't recompile a signed native app, and you wouldn't want them to. Instead, **each agent app's surface is data**: a versioned **spec** that the native shell renders. Johnny edits specs.

### What a spec controls
| Spec part | Examples | Rendered by |
|---|---|---|
| **Navigation** | Sidebar sections, saved views, ordering | Native SwiftUI |
| **Views** | List, table, board, calendar, timeline, gallery, chart, metric tiles, doc, detail panels: each bound to a **query** | Native components from the design system |
| **Queries** | Typed queries over core data ("emails from entity.kind=investor, last 30 days, not replied") | Rust query layer (a safe query DSL, not raw SQL) |
| **Fields** | Custom properties on entities/deals/files ("Kombucha batch: pH, start date") | Native forms |
| **Actions** | Buttons that call tools ("Send to George", "Create follow-up") | Policy engine applies |
| **Automations** | Trigger → conditions → steps (tools, agent asks, approvals) | Scheduler + agent runtime |
| **Instructions** | Agent rules ("Never draft replies to newsletters", "Sign off as Liam") | Prompt assembly |
| **Mini-apps** | Generated HTML/JS panels with a capability bridge | Sandboxed `WKWebView` |

### Spec lifecycle
1. User says, in any app's Ask bar or the **Tune** button: *"Add a column showing when I last replied, and a view of just investors."*
2. Johnny (large or medium model) produces a **spec diff**, validated against the JSON Schema for that agent's spec.
3. The UI shows a **live preview** (rendered side by side) and a plain-English summary of the change.
4. On apply: the spec is committed to a local git repo (`~/Library/Application Support/11am/specs`, via `gix`) with an author and message. The UI hot-reloads.
5. **Rollback:** version history per agent ("Undo Johnny's change from Tuesday"). **Safe mode** (hold ⌥ at launch) loads factory specs.
6. **Try mode:** apply a change for 7 days, then Leo asks "keep it?"

### Customisation levels
| Level | Who | What |
|---|---|---|
| 1. Settings | Everyone | Toggles and preferences |
| 2. **Tune** (Core) | Everyone | Natural-language spec edits to views, fields, instructions, simple automations |
| 3. **Mini-apps** (Johnny add-on) | Power users | Generated panels/tools in a WebView with `window.elevenam.query()`, `.action()`, `.ask()` behind a capability prompt (Johnny can't grant itself permissions) |
| 4. **Scripts** (Johnny add-on) | Power users | JS (JavaScriptCore) or WASM transforms and custom tools, sandboxed, no filesystem or network unless granted |
| 5. **Developer mode** | You (and technical founders) | Johnny edits the actual Swift/Rust source of a local checkout and builds it. Not for end users |

**Guardrails:** schema validation; capability prompts; destructive automations need approval; mini-apps get CSP with no remote code (unless whitelisted); every spec change is an event; and a hard rule that **specs can't change the policy engine** (autonomy levels change only in Settings, by the user).

This is also where your "gimmicky but cute" ideas go: a **template gallery** of specs, mini-apps and automations users can install with one click.

## Security and privacy model

1. **Data classes.** Every record carries a class: `public`, `work`, `private_messages`, `finance`, `health`, `credentials`. Model policies decide per class whether cloud models are allowed. Default: `finance`, `private_messages`, `health` and `credentials` stay **local-only**.
2. **Prompt-injection defence** (emails, web pages and documents are untrusted):
   - **Taint tracking:** any context containing external content marks the job *tainted*. Tainted jobs can't execute `write_external` or `irreversible` tools without explicit user approval, whatever the autonomy settings.
   - **Reader/actor split** (dual-LLM pattern): a reader model summarises untrusted content into structured data. The actor model that holds tools only sees the structured data, never raw text.
   - **No auto-follow:** agents never open links or attachments found in emails without a user action (James can fetch in an isolated profile with no cookies).
   - **Injection test suite:** emails and pages with planted instructions run in CI against every model and prompt change.
3. **Least privilege.** Tools are per agent. Johnny's sandbox has no network and no home directory by default.
4. **Kill switch.** "Pause the team" in the notch and menu bar stops all jobs and schedules instantly.
5. **Transparency.** The model badge on every output (on-device ● / cloud ○ + provider). A Privacy page shows exactly what left the device, when and to which provider (from `model_calls`).
6. **Export and delete.** One-click export of everything (Markdown, EML, CSV, JSON). "Forget" for any memory, person or source, with cascade.
7. **Supply chain.** Pin crate and package versions, `cargo deny` / `cargo audit` in CI, verify model downloads by hash (registry pins SHA-256).

## Lower-end Macs (making it run on less)

See the hardware tiers in [03-ai-brain](./03-ai-brain.md#hardware-tiers). Engineering rules that make the low tiers work:

1. **One resident model.** ModelHost keeps at most one LLM loaded on Tiers A–B. It unloads after N minutes idle (`keep_alive`) and immediately on memory pressure (`DispatchSource.makeMemoryPressureSource`).
2. **Rules before models.** Routing, triage and categorisation try deterministic rules and embeddings first. The LLM only handles what's left.
3. **Reuse Spotlight.** Use `NSMetadataQuery` for name, date, kind and metadata queries instead of building your own index for those.
4. **Index selectively.** Bolton indexes chosen folders, recent mail (90 days full text, older on demand), and skips media.
5. **Defer heavy work.** OCR, embeddings and research synthesis queue for AC power, idle or Night shift.
6. **Small embeddings.** 384-dimension embedder on low tiers (fast, small), larger on high tiers. Re-embed in the background on upgrade.
7. **Shorter contexts.** Cap context windows per tier. Bolton context packs are summarised, not raw.
8. **Native everything.** No Electron, no bundled Chromium, no Docker. WebKit and AppKit are shared system memory.
9. **"Remote brain."** If the user has a second Mac (a Mac Studio or mini at home), 11am can use it as the model host over the LAN or Tailscale. Same for the iPhone.
10. **Honest degradation.** If a feature can't run well, say so: "Image generation needs 24 GB+. Use cloud (Flux API) or skip?"
